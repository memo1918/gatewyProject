# Problems Along the Way

This is a running list of problems I encountered while building the project and what I learned from them.

## 1. Gateway C++ and CMake issues

**Distribution package names:** Fedora packages Paho MQTT as `paho-c-devel` and `paho-cpp-devel`, not `paho-mqtt-c-devel`.

**CMake and linker names:** CMake could not find the library using the generic target name `paho-mqtt-cpp`. Fedora installs the library files as `libpaho-mqttpp3.so` and `libpaho-mqtt3as.so`, so the package names and linker names need to be checked separately.

## 2. The HTTP library is blocking

The HTTP server handles one request at a time in this project. That is acceptable for a single Edge Device because the Gateway only asks for a small reading, but it means a slow request can delay another request.

The Gateway uses a separate worker thread for its HTTP client request. This keeps the MQTT loop responsive while it waits for the Edge Device, and the request has a two-second timeout.

## 3. C and C++ mutexes

In C, a mutex must be unlocked explicitly. In C++, `std::lock_guard` unlocks the mutex automatically when it goes out of scope.
### C
```
pthread_mutex_lock(&my_mutex);   // 1. Lock

shared_data = 42;                

pthread_mutex_unlock(&my_mutex); // 2. Unlock
```

### C++
```
{
    std::lock_guard<std::mutex> lock(my_mutex); // 1. Locks immediately
    
    shared_data = 42;
    
} // 2. Unlocks automatically
```

## 4. MQTT connection status

An MQTT publish acknowledgement confirms delivery to the broker, but it does not prove that the dashboard has processed the message. The Gateway therefore tracks its connection state and uses QoS 1 for sensor data.

The broker can keep the session when MQTT is configured with `clean_session = false`. The Gateway also buffers measurements while it believes the Cloud connection is unavailable and publishes them after reconnecting.

For this project, the broker and Cloud application are assumed to be available. The main failure case being tested is the Gateway's Internet connection. The offline buffer is currently held in memory, so it does not survive a Gateway restart.

## 5. Timestamp handling for offline data

When the Gateway reconnected, it published all buffered measurements at once. The Cloud then used the current time for the incoming data, which destroyed the chronological order in the time-series graph.

The timestamp is now generated by the Edge Device or Gateway before the measurement is buffered. The C++ code appends a UNIX timestamp to the sensor reading, for example `41.25,1727751045`. This allows the Cloud to display delayed measurements in their original chronological order.
